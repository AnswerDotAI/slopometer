**The Theory of warmpy: a warm process is one whose import cache is already full, and warmth is the only difference there is.** Python makes imports expensive once and free ever after, inside one process — `sys.modules` is a cache that dies with its process. warmpy keeps one alive. Everything it does is displacement: your function call, made in a fresh process, executes in an old one.

From that, the single load-bearing invariant: **a warm call and a cold call are the same call.** Same arguments, same stdin and stdout, same cwd and env, same exit code, same Ctrl-C. The user may notice speed and nothing else. This is why the fds travel over the socket rather than being proxied, why cwd and env travel with every call rather than being inherited from whenever the server started, and why the fallback is "run it cold in-process" — the equivalence must survive the daemon's absence, which means the daemon is an optimization and never a dependency.

The server, then, is a cache, and **a cache must be safe to lose and cheap to doubt.** Every failure mode resolves by discard, never by negotiation: stale socket, unlink and respawn; version mismatch, replace the server (a server running yesterday's code is not a stale peer to reason with — it is a *different program*, wrongly answering to our name); lost spawn race, use the winner's; can't spawn at all, run cold. No failure of warmpy's machinery is ever allowed to become the user's error.

Identity follows from equivalence: a server is named by everything that could make its answers differ — target function, interpreter, package versions. Its lifetime is inferred, never commanded: first use starts it, sustained disuse ends it, and there are no lifecycle verbs for users because the working set is the lifecycle.

The user's side of the bargain is one discipline with two halves: the wrapped module stays light (heavy imports are lazy, so the client is cheap by construction), and import-time state is treated as settled — a function that mutates module state behaves differently on the second warm call than a cold run would, and that's the one seam where the equivalence can break, which is why it belongs to the user and not to us.

And the Theory says what warmpy is *not*, which is where simplicity gets defended: it caches imports, never results — result caching would break the equivalence. It is not a task queue, not a service manager, not an RPC framework; the day a design discussion needs one of those words, the proposal is out of scope. The fork-per-request question resolves the same way: fork buys isolation for state-mutating functions, but the Theory already assigns that discipline to the user, so v1 serves in-process under a lock and stays simple.

Test any future decision against one question: *could the user tell, other than by the clock?* If yes, it's wrong. If no, pick the simpler option.
